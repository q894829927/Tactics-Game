# 战场视觉与交互四阶段实施计划（A–D）

> 状态：**A1 参数已定稿，A2–A4 与 B–D 尚未正式开始**。依据 2026-10-13 用户确认的暗黑奇幻战棋目标图。
>
> 当前代码基线：原生 DOM/CSS 10×8 战术棋盘、4 名友军与 6 名敌军、基础移动/攻击/反击、可缩放/拖拽镜头、简单小地图、右侧状态面板、指令菜单。**目标图是视觉/布局标准，不代表截图里的立体场景、角色立绘、装备属性、治疗术等已经开发完成**。
>
> 工作原则：按照 **A → B → C → D** 依次开发与验收。保留现有 `src/engine/battle.ts` 确定性规则与 CI/ECS 独立部署机制；保留交互式地图与 DOM 文字，不允许把整张带 UI 的设计图当作不可交互背景。每次提交 `main` 时执行 [版本规范](VERSIONING.md)：同步升级 `src/version.ts` 并在 `CHANGELOG.md` 记录实际完成的变更。

## 0. 目标与范围

**目标视觉：** 画面左侧为覆盖视口的奇幻森林战场，包含河流、石壁、桥、赤旗营寨和植被层次；右侧为自顶部到底部贴齐的深蓝暗金战斗信息栏；左上角齿轮设置；左下角全局小地图；角色附近浮动指令；中央蓝色我方/敌方回合过场横幅。

**核心验收优先级：**

1. 先消除“中央一小块 10×8 方格 + 四周空白渐变”的观感。
2. 再补齐原创角色头像、兵种图标、单位状态和信息面板。
3. 再增加不破坏现有规则的战斗反馈与可操作性。
4. 最后对齐参考图的细节、响应式布局和真实浏览器效果。

**明确不在本计划中直接承诺实现：** 第二关、完整剧情、永久成长、转职、联网、多套武器系统、真实治疗与魔法/道具/交换玩法。它们需要独立策划与规则实现，不能为了复刻参考图填入假的数值或假功能。

## A 阶段：地图美术重建（P0，第一优先）

**A1 详细工作文档：** [A1-MAP-ART-SPEC.md](A1-MAP-ART-SPEC.md)（已确定坐标、12 项资产清单及场景图层）；[首批资产清单](A1-ASSET-MANIFEST.csv)。

**目标：** 战场达到“完整地图场景”而非局部色块棋盘的观感，优先接近目标图中的森林—河流—石桥—赤旗营寨布局。

**任务拆分**

- **A1 资源规格与场景布局（参数已定稿，待 A2 验证）：** 绘制 10×8 逻辑格与可见装饰场景的坐标/边界对照；确认一套原创场景配色、光照方向和俯视视角；列出需制作的地表、深浅树林、岩石台地、河道、桥、营寨、帐篷、旗帜、火把、云雾素材及来源/使用许可。
- **A2 地图图层重建：** 拆分背景远景、可见地形、单位与战术网格、交互高亮、前景装饰等层；所有图层使用同一镜头变换和坐标映射；地图文本保留 DOM，禁止把 UI 与整张地图烘焙在一张截图上。
- **A3 完整场景填充：** 增加地面纹理变化、树林簇、石壁明暗、河流/瀑布、桥梁与敌方营寨层次；地图边缘用纯装饰区域填充，不暗示格子外能通行。河流和桥若进入可玩格，必须先设计并测试水域/桥梁的真实移动与阻挡规则，否则暂作非可玩装饰。
- **A4 镜头与地图结合：** 维持滚轮缩放（现行 60%–185%）、自由拖拽、重置镜头与格子精确命中；默认视角覆盖左侧主视觉而不是留下大片重复背景；地图裁剪、资源加载失败和宽窄视口时均可继续操作。

**交付物**

- 可单独加载与替换的原创地形资源（禁止将设计稿整图当作地图），附资源清单及许可记录。
- 分层地形渲染代码与逻辑格坐标转换说明。
- 同一可玩关卡在初始缩放、60% 缩放、放大后不同镜头位置的实际浏览器截图。

**退出验收（全部满足才结束 A）**

- 1920×1080 与 1366×768 左侧不再呈现突兀的孤立小方块，周围的地图环境连续自然。
- 森林、石壁、桥、河流、营寨能从画面中清楚区分；资源全部为原创或有使用依据。
- 现有 10×8 寻路、占格、战斗结算未被地形美术误导或破坏。
- 放大/缩小/拖动后点击单位和格子准确，拖动不触发误点击；小地图能正确定位镜头。

**主要风险：** 场景坐标与战斗格坐标错位、图层遮挡交互、装饰桥梁与实际通行逻辑矛盾、大贴图内存与下载开销。优先用一张小型原创场景竖切片验证后再铺完整地图。

## B 阶段：角色与状态栏美术（P1）

**前置：** A 的地图风格及色彩、光照方向基本稳定。

**目标：** 单位和右侧角色面板都能与场景融为一体；数值显示全部来自已有规则或经明确新增的数据模型。

**任务拆分**

- **B1 原创角色头像：** 为现有 4 名友军优先制作角色头像，统一构图、光照、边框、裁剪方式；敌方角色按实际需要逐步补齐。必须可独立替换与记录授权。
- **B2 单位战场标记：** 统一剑/枪/弓/术、敌军/我军标记的线条和配色；处理阵营色、姓名、HP、选中框、可行动/已行动灰化、遮挡层级，缩放后文字仍清晰。
- **B3 右侧角色信息：** 调整头像、姓名/职业、HP、攻击/防御/移动、地形增益、武器与战斗日志排版，和参考图的暗蓝/暗金样式对齐。明确当前代码为“攻击/防御/射程/移动”，**没有真实等级、魔防、回避 +30%、威力/命中/必杀或皮甲装备系统**；如需显示，先扩展规则/数据/测试，不以静态假数值冒充实装。
- **B4 适配：** 右栏从顶部贴齐到底部；较矮视口让日志内部滚动，面板不得互相盖住；移动端按现有页面适配逻辑处理。

**交付物**

- 头像与图标资源目录、命名规则、来源清单。
- 与战斗数据绑定的单位显示组件、右侧信息组件。
- 选中、未选中、残血、已行动、阵营切换的浏览器截图/交互记录。

**退出验收**

- 头像可按角色自动切换，缺失资源时有统一的替代图标；单位标记在 60%–185% 缩放下可辨认。
- 选中不同角色时，HP、攻击、防御、射程、移动、地形加成与战斗状态全部正确更新。
- 对参考图要求但规则尚不存在的字段，**不显示虚假数值**；若采用新字段，附相应计算逻辑与测试。
- 右侧顶部无空白，面板间距一致，日志不溢出覆盖底部版本号。

## C 阶段：战斗交互与反馈（P1）

**前置：** B 的单位定位和信息显示稳定；保留 `Battle` 作为唯一的战斗真值来源。

**目标：** 点击、移动、选目标、结算、待机都有明确反馈，让战斗过程既直观又真实响应玩家操作。

**任务拆分**

- **C1 指令流梳理：** 选中友军 → 显示移动范围 → 移动或选择攻击/待机 → 选目标 → 结算；菜单自动避开视口边缘，右键/Esc 正常撤销，处理移动后不可重复移动及攻击后行动结束。
- **C2 行动预览与提示：** 在引擎现有 `damage`、`inAttackRange`、`reachable` 基础上显示实际可算出的范围、伤害和反击可能性；不引入虚假的命中/暴击概率。缺少目标、状态不允许时，按钮反馈明确。
- **C3 轻量表现：** 单位移动过渡、选中发光、受击闪烁、伤害数字、行动完成效果；表现动画不可改变 `Battle` 结算时间及结果，失败时仍能回到正确状态。
- **C4 完善日志与操作反馈：** 战斗事件按回合、行动类型区分图标及颜色；清楚显示移动、攻击、反击、倒下与回合切换；不编造治疗术等尚不存在的历史事件。

**本阶段不自动开启：** 道具、术法、交换、真实治疗术等。若后续批准，必须先有完整规则，再取消菜单禁用态。

**交付物**

- 行动状态流程说明、必要的战斗事件表现映射。
- 交互回归用例：选择、移动、攻击、反击、等待、敌方回合、胜利、失败、重开。
- 动画前后表现及实际浏览器录屏/截图。

**退出验收**

- 单位被选中、行动中、已结束时的指令与视觉反馈一致；点击非有效区域不会误结算。
- 能根据引擎规则复现预览数值和实际战斗结果。
- 拖拽镜头时不会误触格子，缩放后选中框、行动范围和菜单位置正确。
- 现有确定性战斗测试通过，实际浏览器能完成一局 4v6 战斗。

## D 阶段：UI 细节、性能与综合验收（P2）

**前置：** A–C 功能和资源稳定；D 负责打磨，不承担前几阶段遗留的大型结构重做。

**目标：** 在目标图的桌面尺度下表现一致，并确保浏览器中实际操作、不同分辨率和自动部署可验证。

**任务拆分**

- **D1 小地图与镜头框：** 使用与主地图一致的地形缩略视觉，不只是抽象色块；正确更新我军/敌军位置、白色镜头矩形、缩放与点击定位；必要时独立放大全局地图另立范围。
- **D2 UI 装饰统一：** 设置齿轮、菜单暗金框、右侧状态块、按钮、日志行、颜色、中文字体清晰度与内外边距；版本号从 `src/version.ts` 自动绑定右下角，不能写死。
- **D3 回合横幅与效果：** 蓝色晶体、扫光、我方/敌方回合字幕仅在切换时短暂显示；支持减少动态效果设置；避免挡住必要点击区域。
- **D4 真实浏览器验收：** 1920×1080、1366×768、常见小窗口与手机布局；确认没有横向溢出、状态栏空白、菜单截断、地图拖动/缩放失效、文字模糊；对参考图按模块截图对比。
- **D5 稳定性和上线：** 检查首屏加载、素材体积、较低配置上的渲染帧率、地图长时间操作；执行 `npm run verify`、GitHub Actions 构建/发布，再核对 ECS `.source-sha`，不能用 CI 成功替代线上已更新的证明。

**交付物**

- UI 逐项对照验收表及截图（含残余差异）。
- 浏览器回归测试记录、性能基线与资源体积记录。
- 已通过校验的 Git 提交号、CHANGELOG 更新记录和 ECS 线上版本核对结果。

**退出验收（四阶段共同完成条件）**

- 目标图的布局、场景层次、角色样式、操作菜单、信息面板、小地图、回合表现达到可接受的一致性；差异有书面说明。
- 核心战斗全流程可交互，无用“纯图片”遮挡或替代实际功能。
- 自测与 CI 通过，桌面/移动适配满足上述检查；服务器是否上线明确标注“成功/失败/未核实”。

## 版本安排（建议值，不提前占号）

版本从当前四段式基线递增，遵守 [VERSIONING.md](VERSIONING.md) 与 [CHANGELOG.md](../CHANGELOG.md)。

| 节点 | 建议版本方向 | 升级依据 |
| --- | --- | --- |
| 当前仅记录本计划 | 第四段 +1 | 文档更新 |
| A 内的完整新功能 | 如 `v0.1.1.0` | 新增可验收的地图渲染能力 |
| B 内的完整新功能 | 如 `v0.1.2.0` | 新增可验收的角色/面板能力 |
| C 内的完整新功能 | 如 `v0.1.3.0` | 新增可验收的交互/反馈能力 |
| D 内的功能增强 | 如 `v0.1.4.0` | 新增可验收的小地图/演出能力 |
| A–D 均验收且用户确认重大里程碑 | 才考虑 `v0.2.0.0` | **特别大的整期成果验收** |

注意：中间每次小修复、文档和测试提交都按第四段递增，所以上表并非强制下一版本号。**每次实际更新须同步改 `src/version.ts` 和 `CHANGELOG.md`，如实记录已完成内容，不把计划写成发布成果。**

## 每阶段统一交付格式

每个后续开发任务交付时，应记录：任务编号（A1…D5）、版本号、完成的具体变更、未完成项或风险、对应提交 SHA、`npm run verify` 结果、GitHub CI / 静态发布结果、ECS 实际部署状态，并附必要的浏览器截图。仅写“优化了 UI”不符合更新日志要求。
