# 版本号与更新日志规范（VERSIONING）

> **生效基线：v0.1.0.0（2026-10-13）。**
> 此规范适用于 Tactics-Game 的所有后续开发任务、提交、自动化代理和更新日志。
> 四段式是本项目自定义游戏版本号，不是 npm 的标准三段 SemVer。

## 一、统一规则

游戏版本必须采用 **`vA.B.C.D`**（含前缀 `v`、恰好四段、非负整数、无前导零）。本项目从 **`v0.1.0.0`** 正式开始编号，旧的三段 `v0.1.0` 是历史标记，不参与后续四段式递增。

| 段 | 级别 | 示例 | 条件 |
| --- | --- | --- | --- |
| A | 主版本 | `v1.0.0.0` | 游戏正式发布或正式版重大不兼容变更 |
| B | 特大里程碑 | `v0.2.0.0` | **特别大的开发阶段整体完成并验收**，不能按单个普通功能升级 |
| C | 功能更新 | `v0.1.1.0` | 交付新的独立功能、玩法、子系统或较完整的 UI 交互 |
| D | 最小更新 | `v0.1.0.1` | 修复 Bug、UI 微调、代码性能优化、文档或工程性调整 |

升级某一段时，右侧各段清零；各段不是十进制，不存在 `9` 自动进位。

- 最小更新：`v0.1.0.0` → `v0.1.0.1`
- 功能完成：`v0.1.0.4` → `v0.1.1.0`
- 重大里程碑：`v0.1.7.3` → `v0.2.0.0`
- 正式发布：满足发布条件后才升级到 `v1.0.0.0`。

## 二、每次开发必须同时更新版本和 CHANGELOG

**用户要求：每次更新都记录更新了什么内容，不再允许软件改动后游戏版本保持不变。**

- 以一次**完整的开发交付**为单位更新版本。任务内可以先修改、测试多次，但在提交 `main` 时，应合并成**一次包含代码、版本号、更新日志的原子提交**。不要按测试重跑次数、CI 次数、ECS 轮询次数额外加版本。
- 每次 `main` 开发提交（包含仅文档、测试、脚本、CI 改动）也须遵循：**将 `src/version.ts` 升级一次，并在 `CHANGELOG.md` 顶部新增对应版本的小节，清楚写出本次具体改了什么**。纯文档或工程调整一般用第四段加一。
- 修订版本为默认最低级别；较大独立功能提升第三段，特别大的整体阶段验收才提升第二段；主版本只用于正式版。
- 版本记录必须包含版本号、日期、级别、**具体改动条目**，不要只写“日常更新”或“修复问题”。各版本标题从新到旧排列，保留完整历史。
- 用户指定某个版本号时，遵照该明确要求；不能提前宣称尚未完成或未验收的功能已发布。
- 如果需要多个提交完成同一个功能，优先在本地合并为一个交付提交；如确实需要分别提交到 `main`，**每个提交分别递增并记录**，不能绕过自动校验。

## 三、单一版本来源与包版本

- **唯一的游戏展示版本来源**：`src/version.ts` 中的 `GAME_VERSION`。
- 页面右下角通过 `src/main.ts` 读取这个常量显示；禁止在 `index.html`、其他组件中手写另一套版本号。
- `package.json.version` 是 npm 构建工具字段，必须保持符合 SemVer 的三段格式（例如 `0.1.0`）。它**不等于**本游戏显示的四段号，不能改成 `0.1.0.1` 这种非法 npm 格式。
- `CHANGELOG.md` 的最新版本必须与 `src/version.ts` 完全一致，后续条目按版本号排列。
- 每次修改仓库必须运行 `npm run verify`，其中包含版本检查（`npm run version:check`）和 TypeScript、单元测试、构建检查。
- GitHub CI 和静态站点发布都会运行同一套验证，拒绝遗漏升级和变更日志的提交。

## 四、发布流程与部署校验

1. 开发开始前阅读 `AGENTS.md`、本文件与 `CHANGELOG.md` 最新记录，评估本次版本级别。
2. 完成代码及相关测试，确定版本号；在 `src/version.ts` 更新版本并在 `CHANGELOG.md` 顶部新增完整条目。
3. 运行 `npm run verify`；保证所有变动与版本更新位于同一个提交中。
4. 默认提交 `main`；GitHub Actions 构建 `site` 后由 ECS 定时部署，**不绕过现有 CI 审批与回滚机制**。
5. 单独验证 ECS `/var/www/tactics-game/current/.source-sha` 是否等于预期 Git commit SHA。线上部署 SHA 与游戏版本号是不同标识，不应混用。
6. CI 成功并不代表 ECS 上线已成功；发布总结必须区分代码提交、CI、`site` 构建、ECS 线上版本。

## 五、自动化检查约束

- `tests/versioning.test.mjs` 检查游戏版本格式、展示绑定、更新日志首条与 npm 格式。
- `scripts/check-version-change.mjs` 比较当前提交和第一父提交：**如已经建立四段式版本，必须合法递增且同时修改 `CHANGELOG.md`**。首次迁移允许 `v0.1.0.0` 作为新基线。
- 运行校验需要 Git 提交历史，CI checkout 至少取 2 条历史；不允许通过环境变量跳过正式 CI 版本检查。
- 如果两个开发任务可能并发修改 `main`，必须先获取最新版本号，避免重复号或误覆盖日志。

**旧的“未明确请求发布就不升级版本”约束已废止。今后每次实际开发更新都需要升级版本并记录详细变动。**
