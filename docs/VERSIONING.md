# 版本号规范（VERSIONING）

> 状态：已确定 · 适用于 `Tactics-Game` 后续全部开发与发布。
>
> 本项目处于快速迭代阶段。版本号反映**完成并通过验收的变更级别**，不按 Git 提交次数、自动部署次数或开发日期自动递增。
>
> 本规范采用自定义四段式编号，**不是标准三段式语义化版本控制（Semantic Versioning，SemVer）**。

## 1. 唯一规范格式

```text
v<主版本>.<里程碑版本>.<功能版本>.<修复版本>
```

例如 `v0.0.0.1`、`v0.0.1.0`、`v0.1.1.0`、`v1.0.0.0`。

- **必须显示四段非负整数**，不省略末尾 `.0`，不使用前导零（数字 `0` 本身除外）。
- UI、发布说明和版本文档以带 `v` 的四段式为准。
- **最小版本更新单位是末段 `+1`**，如 `v0.0.0.1` → `v0.0.0.2`。
- 不因为日常修复、样式调整或频繁部署而提高里程碑段。

## 2. 四段定义与升级门槛

| 段位 | 格式位置 | 何时升级 | 举例 |
| --- | --- | --- | --- |
| 主版本 | 第一段 `A` | 游戏达到正式发布标准，或已正式发布后发生重大不兼容升级 | `v0.x.x.x` → `v1.0.0.0` |
| 重大里程碑 | 第二段 `B` | **只有特别大的完整开发阶段**通过验收，涉及一组关联能力整体完成 | `v0.0.x.x` → `v0.1.0.0` |
| 功能版本 | 第三段 `C` | 有完整、可单独体验或验收的新增功能/系统 | `v0.1.0.x` → `v0.1.1.0` |
| 修订版本 | 第四段 `D` | Bug 修复、UI 小调整、已有功能优化、性能优化等小变动 | `v0.1.1.0` → `v0.1.1.1` |

**重要：完成一个「特别大的」阶段才使用 `0.1.0.0`；一般新增功能使用 `0.0.1.0` 或 `0.1.1.0`；微小修改使用 `0.0.0.1`、`0.1.1.1` 这一级别。**

### 进位规则

当某一段升级时，**其右侧所有段重置为零**；不会做四段之间的自动十进制进位，也不限定单段最大值。

- 修复：`v0.0.1.2` → `v0.0.1.3`
- 功能：`v0.0.1.3` → `v0.0.2.0`
- 里程碑：`v0.0.7.9` → `v0.1.0.0`
- 新里程碑后的功能：`v0.1.0.0` → `v0.1.1.0`
- 主版本：`v0.9.8.5` → `v1.0.0.0`（仅在正式发布条件满足时）

多个小修复可合并为一次修订版本；一个阶段内多次提交、CI 通过和 ECS 自动部署**均不强制升级版本**。

## 3. 升级决策：由小到大判断

1. 只是 Git 提交、文档、测试、CI、部署脚本变动，没有用户可感知或兼容性变更 → **默认不升级游戏版本**，保留 Git SHA 追踪。
2. 修复已存在的行为、细微视觉调整、提升现有性能或稳定性 → **末段修订 `D + 1`**（达到发布/验收时）。
3. 新的完整功能（例如镜头缩放、设置菜单、独立道具模块）完成并验收 → **第三段功能 `C + 1`**。
4. 一组相关模块形成一个特别大的、可验收的阶段成果（例如战场 UI、镜头、地图与完整操作流程整体交付） → **第二段里程碑 `B + 1`**；**仅重构了局部代码、尚未验收或只是设计稿，均不得记为完成**。
5. 游戏达到首个正式发布质量与内容要求，且完成正式发布验收 → **第一段主版本 `A + 1`**。

有争议时选择较低级别，除非有明确的阶段目标与验收证据；不要为了数字好看而提前抬升版本。

## 4. 开发期版本示例（规划，不代表已完成）

| 版本 | 示例成果 | 级别 |
| --- | --- | --- |
| `v0.0.0.1` | 最小修改，例如修复文字错位 | 修订 |
| `v0.0.0.2` | 又一次小型修复 | 修订 |
| `v0.0.1.0` | 地图缩放成为可独立验收的功能 | 功能 |
| `v0.0.1.1` | 修复缩放与点击冲突 | 修订 |
| `v0.0.2.0` | 单位指令交互完成 | 功能 |
| `v0.1.0.0` | 一整期战场 UI / 镜头 / 基础交互全部通过验收 | **里程碑** |
| `v0.1.1.0` | 新增完整的装备或道具功能 | 功能 |
| `v0.1.1.1` | 修复新增系统中的问题 | 修订 |

上述版本号**只用于说明规则，不代表仓库已经实现这些能力**；以最新代码、自动化测试、实际浏览器验收和发布记录为准。

## 5. GitHub、npm 与 ECS 的版本区分

**三种信息不可混为一谈：**

1. **游戏展示版本**：四段 `vA.B.C.D`，用于屏幕右下角与「关于」界面，只有在相应功能达到验收标准时才更新。
2. **Git 提交编号（Commit SHA）**：明确标识代码提交，如 `86771c0`；每次修改可变动，但它不是游戏版本号。
3. **ECS 线上源码编号**：`/var/www/tactics-game/current/.source-sha`；用于确认真正上线的提交，不能用大厅的 `.portal-commit` 代替。

仓库 `main` 是默认开发分支；自动发布仍采用 `main → GitHub Actions CI → site 静态发布 → ECS 定时部署`。CI 通过或上线成功**不自动等于正式发布新版本**。

### npm 的版本字段限制（必须遵守）

`package.json` 的 `version` 遵循 npm/Node.js 工具要求，**不得直接写四段号**（例如 `"0.1.1.1"` 是无效 npm 版本）。

- `package.json` 保持合法三段式 npm 版本，如 `"0.1.0"`；其值不作为游戏四段式版本的唯一依据。
- 需要实际接入四段版本时，应另设**单一来源**的游戏版本常量或配置，再同步 UI 和版本信息，不允许多个位置人工写出不一致的版本。
- Git 标签（Git Tag）可使用四段式的 `vA.B.C.D`，但应明确这是游戏版本标签，而非 npm 包版本。
- 未经明确授权，不得为了落实本规范而自动重置现有 `package.json`、UI 版本或补打历史标签。

### 当前仓库的旧标记

当前 UI / `package.json` 中可能仍保留早期的**三段式** `0.1.0` / `v0.1.0`。这是**旧版标记**，不应直接解释为四段式的「重大里程碑已完成」。本次规范落地**仅添加文档和开发约束**；首次实际切换四段式版本时，应明确选择新的起点、记录迁移说明并同时更新所有展示位置，不能出现 UI 与发布记录相互矛盾。

## 6. 每次开发和发布时必须执行

**开发开始前：** 阅读本文件，确定本次是「无需升级 / 修订 / 功能 / 里程碑 / 主版本」，将依据写在工作说明或发布记录中。

**开发完成后：**
- 运行项目既有验证（`npm run verify`），保持游戏玩法与 UI 功能正常。
- 如仅提交代码且未达到新版本验收门槛：保留现有游戏版本，仅记录提交 SHA；**不要每次部署都加一**。
- 如已达到新版本验收门槛：按上述规则选择四段版本，在版本配置、UI 展示和变更日志（`CHANGELOG.md`，启用时）中保持一致；创建标签前核对该提交并确认验收。
- CI 通过、site 分支发布成功后，还需使用 ECS `.source-sha` 验证线上是否真正更新。
- 不提前把规划功能、设计图内容、待验收功能写成「已经发布」。

## 7. 对开发代理的约束

开发代理、Codex 和其他自动化工具执行本仓库任务时，必须在开发前读取本文件：
- **永远不要恢复三段式作为游戏展示版本规范**，也不要把四段号写进 npm `package.json.version`。
- 不要擅自提升第二段「里程碑」，仅在整期大型开发通过验收后提升。
- 不要以自动部署频率、提交数量或 CI 次数作为版本升级依据。
- 未明确提出发布或版本升级时，默认只提交功能更改，保留现有版本；若涉及重大完成节点，应先说明建议版本与理由。
- 默认直接在 `main` 修改，不创建功能分支，除非用户另行指定；保持现有 CI 与独立 ECS 自动部署流程。

本规范优先于仓库旧文档中有关「三段式游戏版本」或「每次提交自动升级游戏版本」的描述。
